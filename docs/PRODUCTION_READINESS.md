## 1. Snapshot comparison fix (done, local tooling)

`npm run staging:snapshot -- compare <label>` used to mark any table with added rows "CHANGED". It also only recognised synthetic records from the ZZ-SYN employee tests, so the ZZ-ACC profiles, access history and checklist showed as "not synthetic". It now:
- **Existing rows:** checks every pre-existing row by primary key, using the columns it had at the snapshot.
- **New rows:** classifies every new row, including rows in tables created after the snapshot. A row is synthetic if it carries a `--tag` or a tag from `.staging-state/synthetic-accounts-*.json`, or references a synthetic account or another synthetic row (`scripts/staging/classify.mjs`, 6 unit tests).
- **Auth:** compares logins and MFA factors without reading secrets. A new factor on an existing account counts as authorized only with `--authorized-mfa <email>`.
- **References to real accounts:** flags any synthetic row that references an existing account, for review.
- **Auth fingerprints:** new snapshots also store them, so later comparisons detect password, ban, role or metadata changes.

Rerun against the pre-test baseline (`staging-pre-acc`):
- every pre-existing row is unchanged;
- 13 additions, all synthetic: 4 profiles, 5 access-history entries, 1 monitor, 1 monitor history row, 1 serial key, 1 onboarding checklist;
- 4 synthetic logins and 1 synthetic factor;
- the only change to an existing account is the authorized TOTP factor.

Run without `--authorized-mfa`, the same comparison fails on that factor, as it should.

## 2. Two-factor for all admin access (proposal 031)

**Today (030):** an admin with only a password has no admin powers (roles, access, restore), but keeps editor-level access. They can read everything, including employee details, and change inventory, checklists, employees and imports.

**Why changing the helper functions isn't enough:** 8 of the API functions read `profiles.role` themselves instead of calling `is_editor_or_admin()`:
- `commit_asset_import`, `commit_bulk_import`, `create_asset`, `create_bulk_item`;
- `onboarding_assign_device`, `perform_bulk_action`, `perform_lifecycle_action`, `perform_swap`.

This was confirmed on the staging catalog and in a disposable copy at 030. Each has exactly one such line.

**Recommended enforcement** (`supabase/proposals/031_admin_mfa_everywhere.sql`, generated by `generate-031.mjs` from the 030 definitions):
- **One decision point.** `session_role()` returns the caller's effective role for the request. It returns *no role* for unknown, anonymous and revoked accounts, and for an admin without a two-factor (aal2) session.
- **Everything routes through it.** `is_known_user()`, `is_editor_or_admin()`, `is_admin()` and the 8 functions use it. Each function changes by that one line, and the generator refuses to run if any other role read exists. No path is left that sees the raw role.
- **Own profile only.** An admin without two-factor can still read their own profile row (new `profiles_select_self` policy), so the app can send them to the code prompt or the Security page. Nothing else is readable or writable.
- **Promotion needs an authenticator.** Making someone an admin through the app requires that they already have a verified authenticator. Otherwise their password alone could enrol a factor and reach admin powers. A direct database connection can still set roles, for bootstrap and recovery.
- **Others unaffected.** Editors, scanners and viewers are unchanged.

Tested (`proposal-031.db.test.ts`, 7 tests):
- each of the 8 functions differs from 030 by exactly one line;
- a password-only admin sees only their own profile, and every callable function plus 14 realistic writes change nothing;
- with two-factor, full powers;
- editors and viewers unaffected; revoked accounts still blocked;
- the promotion rules hold;
- the rollback (`031_down.sql`) restores 030 exactly.

**Why not other approaches:**
- **PostgREST pre-request hook** (one check before every API request): it covers everything, but lives in role configuration outside the migrations, is invisible to the schema history, and can be lost if the platform rewrites that configuration. It's a reasonable second layer later, not the primary control.
- **Restrictive RLS policies:** they don't reach the security-definer functions above.

**Also needed for 031 (app):**
- If a password-only admin has a factor, the app already shows the code prompt.
- If they have none, the app must open the Security page instead of empty screens.
- The Access & Roles screen should explain the "needs an authenticator first" error.
- This is small, but it's a frontend change and needs approval.

**A gap that exists today:** until an admin enrols, someone with their password can enrol their own authenticator and reach admin powers. Mitigations:
- the production admin enrols immediately after 030;
- the preflight lists admins without a verified factor;
- 031's promotion rule covers future admins.

As far as I know, Supabase requires an aal2 session to add a second factor once one is verified. That should be confirmed on staging with a synthetic account (plan step B4).

## 3. Blocking sign-in for revoked accounts (proposal 032)

**Today:** a revoked account can still sign in and refresh its session. It sees nothing and can change nothing, because the database checks every request, but it still holds a working login.

**Recommended process** (`supabase/proposals/032_auth_block_on_revoke.sql`): in the **same transaction** as Remove access:
- **Block sign-in:** set `auth.users.banned_until` 100 years ahead, which is what Supabase's own "ban" does. Supabase Auth then refuses password sign-in and token refresh.
- **Sign out everywhere:** delete the person's Auth sessions; refresh tokens cascade.
- **Tokens already issued:** they stay valid until expiry (at most 1 hour) but grant nothing.

| Situation | What happens | Recorded |
|---|---|---|
| Normal revoke | Access removed, sign-in blocked, sessions ended | `revoked`, `auth_block = applied` |
| Account already banned in the dashboard | That ban is left exactly as it is; sessions still ended | `auth_block = not_ours` |
| Blocking fails (e.g. Supabase changes its Auth tables) | **Access is still removed.** The block runs in its own subtransaction, and the app shows a warning | `auth_block = failed`, `auth_error` |
| Restore | Lifts only a block that Remove access set; a dashboard ban stays | `restored`, `lifted` / `not_ours` |
| Lifting fails | Access is restored; sign-in stays blocked until retried | `restored`, `failed` |
| Repair | `retry_auth_sync(user)` applies or lifts as the access state requires (admin with two-factor only) | `auth_sync_retried` |
| Detection | `auth_block_mismatches()` lists every disagreement between access state and Auth state. Run it in staging verify, the production smoke check and periodic review | — |

**Why this avoids database/Auth inconsistencies:** one transaction means there's no half-done state, except the deliberate "access removed, block failed", which is recorded, shown, detectable and repairable. The reverse failure (access restored but still blocked) fails closed.

Tested (`proposal-032.db.test.ts`, 7 tests, with the Auth tables stubbed). The tests cover each row of the table above; they also check that only admins with two-factor can retry or list mismatches, that nobody can call the Auth helpers directly, and the rollback. The rollback restores 030 and deliberately leaves every block and all audit columns in place.

**Alternative:** an Edge Function using the service-role key and Supabase's admin API (the documented interface). The cost is a second system, a second deploy, a service key to protect, and no shared transaction, which means a reconciliation job becomes mandatory. I recommend 032, provided staging confirms that Supabase Auth honours the ban (plan step B4). 032 writes two Supabase-managed tables directly (`auth.users.banned_until`, `auth.sessions`); that is the trade-off you're choosing.

**Runbook rule:** never delete a login in the Supabase dashboard. `profiles` cascades from `auth.users`, so the delete either fails, because the person authored history, or silently removes their profile. Use Remove access.

## 5. Migration compatibility checklist, 021–030

Production's current state is unknown; the preflight reports it. All of these migrations ran on staging (PostgreSQL 17.11) through the same runner, one transaction each. Every one fails *safely*: an error rolls back the whole migration.

| 022 | 021; `auth.users.is_anonymous`, `auth.uid()`, `auth.jwt()` | the policy `profiles.profiles_update_admin_or_self` is missing or renamed | anonymous profiles pinned to viewer (backup in `private`) | yes | anonymous accounts; Auth objects; dropped names | anonymous session reads nothing |

| 024 | 023 | — | derives `laptop_outcome`; conflicts set `outcome_needs_review` | yes | — | review flags listed |
| 025 | — | — (adds an enum value; nothing uses it in the same transaction) | none | yes | — | `lost` available |
| 026 | 025 | constraint `onboarding_checklists_assigned_asset_id_fkey` missing or renamed | employees + register backfilled from assignments; checklists linked | yes | dropped names | register matches every device (smoke) |
| 027 | 026 | — (duplicate serials are kept and listed, not refused) | `serial_keys` built | yes | duplicate serials | duplicates listed |
| 028 | 027 | employees share a normalized work email | new columns, empty | yes | shared emails | — |
| 029 | 028 | Bulk Stock items share a normalized name + category; `commit_bulk_import(text, jsonb)` missing | new column/table | yes | shared bulk names; dropped names | re-import adds nothing |

Applies to all of them:
- **Size:** small tables (hundreds of rows), so each migration takes seconds and locks briefly.
- **Schema cache:** Supabase reloads the API schema cache automatically after changes.
- **Order:** database first, then the app. The new app needs the new schema; old app builds keep working except "delete profile", which now fails safely.
- **Hand-made objects:** anything created in the dashboard that the migrations don't know about can change the security picture. Hand-made policies, API-callable security-definer functions and tables without RLS are **STOPs** in the preflight.

## 6. Production preflight procedure

The preflight never writes; it runs in a read-only transaction. It's tested on disposable databases (`preflight.db.test.ts`, 6 tests): a clean database at 020 shows only the expected 021 fix-up, and four kinds of drift are caught. On staging it reports no STOPs.

**What the owner runs, from a trusted machine:**
1. Download the production CA (see section 4).
2. Run:
   `PREFLIGHT_DB_URL='…' PREFLIGHT_DB_SSL_CA=certs/supabase-prod-ca.crt node scripts/production/preflight.mjs`
   The connection string comes from the environment only, never from a file in the repository.
3. Keep the output. It contains counts and object names, no personal data except Bulk Stock names if duplicates exist. Send it for review.
4. **Dashboard checks** (Auth settings aren't visible from the database):
   - anonymous sign-ins **off**;
   - TOTP multi-factor **enabled**;
   - point-in-time recovery or daily backups enabled, with the latest backup time noted;
   - PostgreSQL version noted.

**What the preflight checks:**
- **Connection security:** TLS verified.
- **Platform:** PostgreSQL ≥ 15; the Auth objects the migrations use.
- **What's applied:** recorded migrations, 001–020 present, which of 021–030 are pending, and the 021 state.
- **Every object a pending migration drops by name exists**, or is created earlier in the plan.
- **Drift:** policies, API-callable security-definer functions and tables without RLS that no migration created.
- **Data conditions:** anonymous accounts, duplicate serials, shared work emails, shared Bulk Stock names.
- **Admin readiness:** admins and their two-factor status.
- **Size:** row counts.

**A STOP means do not migrate.** Each STOP names the decision it needs.

## 8. Proposed execution plan

Each phase needs your approval before it starts.

**A. Local (approved, done):** everything in sections 1–6. DB suite, frontend suite, lint, tsc and build all green; committed locally.

**B. Staging (needs approval):**
1. **CA verification on.** You download the staging CA; I set `STAGING_DB_SSL_CA`.
2. **Make 031 and 032 real migrations, if D1 and D2 are approved.** Move them into `supabase/migrations` and add the small app changes:
   - Security-page routing for password-only admins;
   - the promotion error message;
   - the sign-in-block warning and Retry button.
   Then retest everything locally.
3. **Apply to staging.** Snapshot, restore check, rehearsal on the restored copy, apply, row-level comparison.
4. **Synthetic-account checks** (temporary accounts only, like ZZ-ACC):
   - a revoked account's password sign-in **and** token refresh are refused by Supabase Auth;
   - restore re-enables sign-in;
   - a password-only admin sees only the Security page;
   - an account with a verified factor can't add a second one at aal1.
5. **Read-only browser checks and final comparison.**

**C. Production preflight (needs approval; you run it):** section 6, then a review of every STOP and INFO line, and decisions D3–D7.

**D. Production change window (needs approval):** as in `docs/PRODUCTION_MIGRATION_PLAN.md`:
1. freeze writes; take a fresh backup; preflight again (must be clean);
2. apply migrations one at a time, checking after each;
3. deploy the frontend from the same commit;
4. admins enrol in two-factor;
5. smoke checks (including `auth_block_mismatches()` if 032 is adopted).
